# 5 October: sound is feedback, not an RL reward

## Prerequisites and intuition

A reward is a number returned by the environment. A sound is a presentation cue for the human. They may describe the same outcome, but changing a sound must not change what the agent learns. Review [episode traces](2026-10-04.md) for rewards/returns and [round revisions](2026-10-01.md) for accepted commands.

For example, winning still yields reward +1 with sound muted, unsupported or enabled. A pleasant sound does not make an action more valuable in the learning code. This boundary keeps presentation polish from changing the experiment.

## Map confirmed transitions to cues

Let v be the previous view's revision and v′ the new revision. Only consider a cue when **v′ = v + 1**. Initial loading has no previous view. A repeated view has v′ = v. A jump larger than one means this client missed transitions, so this small preview does not guess which sound to play.

After that revision check:

1. Accepted deal into an active hand → deal cue.
2. Accepted nonterminal hit → hit cue.
3. Terminal reward +1 → win cue; -1 → loss cue; 0 → push cue.
4. Missing/invalid data or no recognized transition → no cue.

A busting hit gets the loss cue rather than both a hit and loss cue. These labels are categories, not playable audio yet. The later browser integration must invoke them only for a confirmed successful local action response; refreshes and error responses remain silent even if another tab changed the state.

## Code walkthrough

[foundations/sound-events.js](../../foundations/sound-events.js) exposes `transitionCue(previous,current)` as a pure function. It reads two views, returns a cue name or `null`, and never modifies either view. Early returns guard missing snapshots, nonconsecutive revisions and invalid states. Terminal reward selection happens before the nonterminal hit case.

The JavaScript helper can be tested by Node without running a browser or loading audio. Separating classification from audio playback lets us test gameplay semantics independently of hardware and browser audio permission behavior.

## Worked examples

Previous: revision 1, active hand. Current: revision 2, last command hit, still active, reward unset → **hit**.

Previous: revision 1, active hand. Current: revision 2, last command hit, done=True, reward=-1 → **loss**. The numeric reward remains -1 regardless of whether that cue is later played.

Refreshing the same revision-2 view → **null**, preventing replay. Seeing revision 4 directly after revision 1 → **null**, because a single sound cannot faithfully explain several missed transitions.
