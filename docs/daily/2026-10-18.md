# 2026-10-18 — sound cues belong to the interface

## 04:00 checkpoint: opt-in audio for the public-rule table

### Prerequisites and intuition

The browser displays observations returned by the Python game, and it sends commands back to the authoritative session. A valid action changes the game revision; a refresh only reads state. Sound is **presentation feedback** about a confirmed transition. It must never decide whether an action is legal, invent a reward, or change the bankroll.

Browsers require a user gesture before audio can start. The player therefore begins silent, offers an Enable/Mute button and volume slider, and stays playable when audio is unsupported or blocked. The existing synthesized Web Audio player is reused; no audio files or network services are added.

### Event rule and worked examples

After an accepted command, compare the old and new revisions. If `new_revision != old_revision + 1`, there was no single accepted transition to announce. For a next revision, cues are selected from the command and authoritative settled result:

```text
cue = no cue, unless command was accepted
deal / split in a live round -> deal cue
hit / double in a live round -> hit cue
settled normalized profit > 0 -> win cue
settled normalized profit < 0 -> loss cue
settled normalized profit = 0 -> push cue
refresh / rejected request / unknown command -> silence
```

For example, revision4 to revision5 after a Hit in a still-active hand gives a hit cue. If that Hit busts and settles at normalized profit−1, the outcome cue is loss instead. Standing on the second hand of a split round may not settle yet, so it stays silent until the authoritative aggregate round result is available. An opening natural settled during Deal immediately uses that final normalized outcome.

### Coding walkthrough

`public_game/local_game.py` serves the public cue classifier and the existing `foundations/sound-player.js` from the loopback server. The HTML loads those modules and adds accessible labels, a pressed-state toggle, a volume control, and a live sound-status message. The command handler classifies a cue only inside the successful HTTP response branch, before rendering the new state. The classifier in [sound_events.js](../../public_game/sound_events.js) is pure: it reads previous/current snapshots and the submitted command, then returns a cue name or `null`. The shared [sound player](../../foundations/sound-player.js) handles the user gesture, volume, mute, persistence, and graceful browser failure.

Run the UI at `python3 -m public_game.local_game --port 8766 --seed 7`. Audio is optional: deal/hit/split/outcome cues use short synthesized tones; preferences persist, but the user must enable audio again after a page reload because the browser gesture permission is page-local.

### Limits and exercise

This only adds audio to the local single-session inspector. It does not make the game public or production-ready. We did not perform an acoustic listening test, a screen-reader audit, or a complete cross-browser permission audit. Audio can be disabled, unsupported, denied, or muted without blocking play. Sound never changes game rules or results.

## 05:00 checkpoint: announce accepted turns and final outcomes

### Prerequisites and intuition

The game already places a polite live region on the page with `role="status"` and `aria-live="polite"`. A screen reader can announce text changes there. Until now, an accepted action only said “Command accepted,” leaving a player who cannot see the table to infer the new hand total and available choices. The server response contains the authoritative visible state, so the UI can describe that snapshot without inventing or changing game logic.

### State-to-message rule

For an accepted command, derive the announcement from the response:

```text
player_turn -> active hand number + hard/soft/bust total + dealer up-card + legal actions
settled -> outcome sign + net chip profit
ready -> prompt for wager and Deal
```

Worked example: suppose the accepted response has active hand index `1`, total `12`, no usable ace, dealer up-card 10 of spades, and legal actions `hit, stand, double`. The text is “Hand 2. Hard total 12. Dealer shows 10 of spades. Available actions: hit, stand, double.” A settled state with profit `-60` in half-chip units is announced as a loss of `-30` chips because the public display uses two half-chip units per chip. For a split round, that message uses the aggregate final round profit; it does not announce an intermediate hand as if it were the final result.

### Coding walkthrough

`stateAnnouncement` in [the public table](../../public_game/local_game.html) receives the response snapshot after a successful request and builds a sentence from `phase`, `hands[active_hand]`, `dealer`, `legal_actions`, and final `profit`. The status text is updated in the accepted-response path; rejected actions retain the server error and Refresh retains its neutral message. Since `#status` is already a polite live region, no change to focus or keyboard behavior is needed. This is presentation-only: Python still validates actions and calculates totals, legal choices, and reward.

All three existing browser journeys passed, with no page errors.
