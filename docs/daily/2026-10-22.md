# 2026-10-22 — validate a custom wager before Deal

## 04:00 checkpoint: help prevent an unaffordable wager

### Prerequisites and intuition

The game stores money as integer half-chips so a 3:2 blackjack payout stays exact. The wager input accepts whole chips, so a typed amount `w` costs `2w` internal units. A browser check can give immediate feedback, but it is only a usability guard: users can alter browser code or send a request directly, so the Python session must continue to validate every wager.

### Rule and worked example

For balance `B` in half-chip units, the browser enables Deal only when:

```text
valid(w) = w is a positive safe integer
affordable(w, B) = 2w <= B
can_deal = ready_phase AND not_busy AND valid(w) AND affordable(w, B)
```

If `B = 20`, the player has 10 whole chips. A wager of 10 is valid and affordable (`2 × 10 = 20`); a wager of 11 is valid but unaffordable (`22 > 20`). A wager of zero is invalid. The field uses `aria-invalid` and points to a short instruction, while Deal becomes disabled for invalid or unaffordable input.

### Coding walkthrough

In [`public_game/local_game.html`](../../public_game/local_game.html), `syncWagerButtons()` parses the input, checks integer/range rules and the current visible balance, marks the field, and updates Deal. `render()` invokes it after each accepted server snapshot; the input event invokes it as the user edits. The server-side session remains the final authority. The browser test temporarily supplies a low-balance snapshot to cover unaffordability, then restores the real snapshot before continuing its server-backed journey.
