# 1 October: what may the player see?

Today's bridge from RL to the web game is **state versus observation**. Prerequisites: a Python dictionary maps names to values, a list holds card values, and `None` means no disclosed value. Review [Lesson 1](../lessons/01-agent-environment.md) for the agent/environment loop and [Lesson 6](../lessons/06-q-learning.md) for action values.

## Intuition and information boundaries

The environment knows both dealer cards. The player and bot should not know the hole card while deciding. Sending it to a browser and merely drawing a card back would still disclose it: the browser would possess the data. Instead, the Python environment must omit it from the visible data.

Write the relationship as observation o = f(internal state x). A useful check is: if x and x′ differ only in a hidden dealer card, then f(x) = f(x′) before reveal. For example, player [10,7], dealer [6,A] and player [10,7], dealer [6,10] both disclose dealer [6,None]. The dealer total must also be omitted; otherwise it can reveal information about the hidden card.

The RL agent still receives `(player_total, dealer_upcard, usable_ace)`. The browser view includes visible card values for drawing the hand; it is not automatically the agent's observation schema. This boundary alone does not prove an observation is Markov: whether it contains all information needed to predict the next transition depends on the rules. The planned finite shoe introduces additional issues absent from replacement draws.

## Code, step by step

[Blackjack.visible_hand](../../foundations/blackjack.py) is a small read-only view of the existing Foundations engine:

1. Reject access before the first reset because no hand exists yet.
2. Score the player's visible cards with the existing `score_hand` function.
3. Copy player cards into a new list.
4. While active, return dealer `[upcard, None]` and `dealer_total=None`.
5. At termination, reveal copied dealer cards and their total. Return no legal actions.
6. Include the exact Foundations rule label so future presentation cannot silently imply six-deck rules.

A copy matters: editing a returned list must not alter the authoritative environment. Reading the view must not draw cards or advance its random generator. A later web service must use this explicit view, never serialize the entire environment or its random seed/state.

Card values are not full ranks or suits: 10/J/Q/K share the value 10 here. A visual preview must label that limitation instead of inventing exact identities. On player bust, this teaching view reveals the existing dealer hand without making the dealer draw; a dealer total below 17 then is expected. The policy for this preview is reveal on all terminal outcomes.

## Worked scoring example

Player [A,6] starts with ace=1: base sum = 1+6 = 7. Since 7+10 <= 21, promote one ace to 11, yielding total 17 and usable ace=True. Hit a ten: base sum = 1+6+10 = 17; adding ten would give 27, so the ace stays 1. Total remains 17 but usable ace becomes False. The dealer hole card remains hidden during that nonterminal hit.

## 04:00 checkpoint: who owns the next action?

Added [GameSession](../../foundations/session.py), a small in-memory controller around the same environment. Run `python3 -m foundations.session --seed 7`, then enter `deal`, `hit`, `stand`, and `quit`. This is a playable terminal teaching path; the browser transport is still pending.

The controller owns the round and accepts only command names plus an expected revision. It does not accept card lists, totals or rewards from the caller. A revision is an integer version of the current view, starting at zero. For each accepted command, new revision = old revision + 1. A request is accepted only when expected revision = current revision and the command is legal for the round phase.

Worked example: deal at revision 0 produces revision 1. Hit with expected revision 1 produces revision 2. A repeated copy of that same hit still carries revision 1, so it is rejected before drawing another card. Fetch the current view after a stale request; do not blindly retry it with the new revision. This is rejection of duplicates, not replaying a cached successful response.

Code walkthrough: `command` checks revision, then command name, then round phase, then calls the authoritative environment. Only success increments the revision. `view` delegates card disclosure to `visible_hand`, exposing no seed or hidden card. `reward=None` means no completed result yet; a completed push has reward zero. A new deal clears the previous reward. Each GameSession owns a separate environment.

Measured seed-7 walkthrough: deal gives player [6,3] total 9, dealer [7,None]; hit adds ace for soft 20 while the hole card stays hidden; stand reveals dealer [7,10] total 17, reward +1, revision 3. The terminal command exercise and all **66 tests passed**, including four session tests for lifecycle, duplicate hits, invalid-command nonmutation/random-stream preservation, detached views and isolated sessions.

Limitations: this is not an HTTP service, authentication, persistence, expiry management, or a concurrent server. A future server must serialize the entire revision-check-and-update operation; a revision counter alone does not prevent concurrent races or identify a user. No public deployment or full six-deck rules are claimed.
