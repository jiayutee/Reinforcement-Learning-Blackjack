# 8 October: atomic transitions and trustworthy learning data

## Prerequisites and intuition

A state is the environment's current information: cards, balance, turn and random-generator state. An observation is the portion shown to the player or agent. A transition changes state after an accepted command. A revision is an integer counting accepted commands, starting at zero.

Imagine a deal subtracting your wager and drawing two cards, then failing. If retrying continues from that half-finished state, you pay twice or receive a different distribution of hands. We need an **atomic transition**: either the whole command succeeds, or the old state remains intact.

This matters for RL too. An episode should record accepted transitions, not failed attempts that secretly change the environment. Atomicity does not make a partially observed game Markov; it prevents implementation failures from corrupting the intended dynamics.

## Code, step by step

[PublicSession](../../public_game/session.py) now owns opening deals:

1. Compare the supplied revision with the current revision. Reject a stale request before doing anything else.
2. Reject a new deal during an active hand and validate funds using yesterday's wager checks.
3. Copy the private shoe, including its random-generator state. Prepare the reserve and draw on this candidate only.
4. Reuse yesterday's pure `opening_round` calculation.
5. Replace the authoritative bundle with the candidate shoe, resulting balance, revision+1 and opening result.
6. Build a detached visible snapshot. An active dealer's second card and total remain hidden; a settled natural reveals them.

If steps 3–4 raise an exception, step 5 never happens. Discarding the candidate preserves both cards and future randomness. Copying a six-deck shoe is a simple bounded implementation choice for this local prototype, not a measured high-concurrency optimization. There is no concurrent server access yet; locking or serialization is still needed before sharing a session between concurrent requests.

## Equations and example

Let S be the entire private state and c a command. For an accepted command, S' = T(S,c) and revision' = revision+1. For a rejected or failed command, S' = S and revision' = revision.

For a natural with starting balance B=200 units and wager w=20, credit=50. Therefore B'=B-w+credit=230, profit=B'-B=30. A repeated request carrying revision 0 is rejected after the first success moves the revision to 1. Reading a snapshot never adds another credit.

## 04:00 checkpoint: complete a hit/stand round

The session now supports `act('hit', revision)` and `act('stand', revision)`. This extends the same candidate-copy boundary to player and dealer draws. It supersedes the opening-only limitation above, but double and split remain unsupported; this is not the full public rules profile.

A hit adds one card. Below 21, the hand remains active and dealer information stays hidden. At 21 or above, or after stand, the hand completes. A busted player loses without further dealer draws. Otherwise the dealer draws while total <17, including standing on soft 17. The existing settlement function computes credit; the session adds it once and commits revision+1. Revealed snapshots include **all** dealer cards, not just the initial two.

For an ordinary loss, the debit already occurred at deal. With B=200 and w=20, the balance during play is 180. Losing credits zero, so final balance remains 180 and completed profit is -20. Do not subtract the wager again on loss. Intermediate play has no completed profit (`None`); a push has completed profit zero.

Run this seeded example from the repository root:

```sh
python3 - <<'PYCODE'
from public_game.session import PublicSession
s = PublicSession(seed=7)
v = s.deal(20, 0)
print(v['phase'], v['balance'])
if v['phase'] == 'player_turn':
    v = s.act('stand', v['revision'])
print(v['phase'], v['balance'], v['profit'], v['dealer_total'])
PYCODE
```
