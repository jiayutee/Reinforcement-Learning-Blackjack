# 4 October: read a hand as an RL episode

## Prerequisites and intuition

An episode is one complete hand. An observation describes what the agent can see, an action is hit or stand, and a reward is the immediate result of that transition. A Python list can store transitions in order; a dictionary names their fields. Review [Lesson 1](../lessons/01-agent-environment.md) and [single-step inference](2026-10-03.md) if needed.

The table previously showed only its latest hand and last action. A current-hand trace lets us inspect the entire observation → action → reward → next observation sequence. This is useful both for learning and for checking implementation behavior. Recording experience is not the same as training: the frozen policy remains unchanged.

## Worked example: reward versus return

With seed 7, Deal gives observation (9,7,False). Hit leads to (20,7,True), reward 0, unfinished. Stand leads to a terminal win, reward +1. The final observation is also (20,7,True): unchanged observation does not mean the hand continues. Always inspect `done`.

For gamma=1, the return from decision t is the sum of subsequent rewards:

1. Last decision: G₁ = r₂ = +1.
2. First decision: G₀ = r₁ + G₁ = 0 + 1 = +1.
3. The hit's immediate reward was zero, but its eventual return was +1 in this hand.

Monte Carlo can use these completed returns after the hand. TD methods use a next-state estimate during the hand instead. One recorded win is a sample, not the true expected value or proof that an action is optimal.

## Code walkthrough

[GameSession](../../foundations/session.py) now includes `transitions` in its detached view:

- A new deal clears the current-hand trace.
- Before each accepted hit/stand, it derives the observation from visible player total, dealer upcard and usable ace.
- The existing environment executes the action once and returns next observation, reward and termination.
- The session appends exactly those five fields, then advances its revision normally.
- Rejected/stale requests append nothing. Reading the view deep-copies the nested trace so callers cannot alter stored observations.

The trace omits dealer hole cards, seed/random-generator state and internal card lists. It has only the established learning observation. It includes terminal transitions but no invented action after termination. Deal is setup, not a learning action, so it is not a trace row. This is a current-hand list, not cross-hand storage or a training dataset service.

## Run it

```sh
python3 - <<'PYCODE'
import json
from foundations.session import GameSession
session = GameSession(7)
session.command('deal', 0)
session.command('hit', 1)
view = session.command('stand', 2)
print(json.dumps(view['transitions'], indent=2))
rewards = [row['reward'] for row in view['transitions']]
print('Return from first decision:', sum(rewards))
PYCODE
```

Expected: two rows, rewards 0 and +1, done flags False then True, return +1. The browser receives the trace in its state response, but a readable trace panel is the next checkpoint.
