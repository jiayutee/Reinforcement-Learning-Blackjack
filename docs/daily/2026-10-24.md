# 2026-10-24 — verify server-side wager authority

## 03:00 checkpoint: reject an unaffordable direct request

### Prerequisites and intuition

Yesterday's browser lesson added an immediate disabled state for an unaffordable custom wager. That improves feedback, but a user can change JavaScript or send an HTTP request without using the button. The browser is not a trusted source of money or game results. The Python session must repeat the validation before it changes the balance or draws cards.

### Rule and worked example

The request carries a stake in half-chip units. For starting balance `B`, a valid whole-chip wager `w` is represented as `stake = 2w`, and the server accepts it only if:

```text
type(stake) is int AND stake > 0 AND stake is even AND stake <= B
```

With `B=200` half-chip units, a request for `stake=202` is over budget. The endpoint should return a conflict and the exact pre-request state. It must not debit the balance, advance the revision, or consume any shoe cards.

### Coding walkthrough

[`tests/test_public_http.py`](../../tests/test_public_http.py) starts the real loopback HTTP handler, obtains its per-process token, snapshots `/state`, then sends an authenticated but unaffordable `deal` request. It checks the 409 response, the validation message and equality of the returned state with the original snapshot before making the valid control request. The production decision belongs to `PublicSession.deal()` and `validate_wager()`, not this test or the browser.

### Runnable experiment

From the repository root:

```sh
python3 -m unittest discover -s tests
```

Expected: the full suite passes, including the loopback endpoint rejection and state-nonmutation check.
