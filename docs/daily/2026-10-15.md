# 15 October: visible features and usable aces

## Prerequisites and intuition

An observation contains information a player can see. A feature is a useful value derived from that information. Hand total and whether an ace can count as11 are examples. Computing a feature from visible cards does not reveal the hidden dealer card; deriving dealer totals from private cards during play would.

The public browser now displays each hand's hard/soft/bust total, supplied by existing Python scoring through the visible snapshot. Dealer total appears only after settlement. JavaScript presents these features without duplicating scoring rules.

## Worked equations

Count every ace as1 first. Let s be that sum. If there is an ace and s+10<=21, promote one ace to11: total=s+10 and usable_ace=True. Otherwise total=s and usable_ace=False.

A+6: s=7, s+10=17, so soft17. AddK: s=17 and27>21, so hard17. Add5: s=22, so bust22. The ace cannot be reduced again because it already counts as1.

These features help a learning agent distinguish equal totals with different drawing risks. They are not a complete public-game observation by themselves: split context, legal actions, other hands and finite-shoe history can matter. Adding visible totals is not training a policy or proving the observation is Markov.
