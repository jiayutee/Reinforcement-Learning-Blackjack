# 10 October: keep the reward denominator fixed

## Prerequisites and intuition

A stake is the amount committed to a hand. Profit is the final balance change, excluding returned stake. A normalized profit expresses that change in units of the original wager, allowing differently sized wagers to be compared.

Doubling changes the final stake. It must not change the denominator used to measure the round. Otherwise a doubled loss looks just like an ordinary loss, hiding its extra cost from learning and evaluation.

## Equations and worked example

Let b be the initial wager, w the final stake and P the net profit. The completed round metric is R=P/b.

1. Start with 200 half-chip units and b=20.
2. Deal debits 20, leaving 180.
3. Double debits another 20: w=40 and balance=160.
4. A win credits 80, leaving 240. P=240-200=40.
5. R=40/20=+2. Dividing by final stake would incorrectly give 40/40=+1 for this chosen round objective.

A double loss has P=-40 and R=-2. A push has R=0. An eligible natural has P=1.5b and R=1.5. These are game outcomes, not predictions or promises about average performance.

With gamma=1 and reward assigned only at round completion, episodic return is the sum of intermediate zeros and this terminal R. For future split rounds, sum all hand profits first, then divide by the same initial wager. The existing Foundations reward bounds and evaluation formula cannot be reused unchanged.

## Coding step by step

[OpeningRound](../../public_game/opening.py) now saves `initial_stake` when the deal starts. The existing `stake` field still tracks the current hand's stake. The session's immutable replacement on double changes `stake` and preserves `initial_stake`.

[PublicSession.view](../../public_game/session.py) exposes both fields and `normalized_profit`. Before settlement this metric is `None`, meaning unfinished, rather than a completed push. Once settled it is `profit / initial_stake`. A new deal stores its own denominator and clears the previous result.

This is a snapshot metric, **not a reward event on every read**. A future RL adapter must emit the terminal reward once for the accepted transition. Refreshing a snapshot must not generate another training transition. No adapter or agent has been connected yet.

Added a pure [split construction](../../public_game/splitting.py), with [deterministic tests](../../tests/test_splitting.py). It accepts an equal-rank pair and two supplied new cards, returning two immutable hand records and the balance after one additional stake. It does not draw cards, commit a session or enable the split command yet.

Example: start at 200 units, deal wager20 -> balance180. Split 8+8 with new cards 3 then K -> hands (8,3) and (8,K), each stake20, balance160. The total committed stake is40, but initial wager remains20. If one later wins and the other loses, their profits +20 and -20 sum to0; normalized round profit is0/20=0. Settlement must eventually wait for all hands and sum their results.

Coding steps: validate funds and a current hand count below four; verify equal **rank** (J+K is not a pair); pair each original card with its corresponding added card; record split context; subtract one matching stake. Split aces are marked complete after their one added card, including A+A, which cannot resplit under our rules. An A+K created by splitting earns ordinary 21 payouts; it is not a natural.

## 05:00 checkpoint: validate a split before drawing

Extracted `validate_split` from the split constructor so the future session can check eligibility before consuming cards. The constructor calls the same validator again, keeping one rule definition. It checks funds, equal rank, fewer than four current hands and the ban on resplitting aces. Session phase/revision checks remain the session's responsibility.

Why before drawing? Suppose balance is19 units and the extra stake is20. The action must be rejected without inspecting or consuming the next cards. Learning data should reflect accepted actions only. Reusing a predicate's rules for construction also prevents the displayed options and actual behavior from drifting apart.

The new deterministic test enumerates 13×13 rank pairs ×4 hand counts ×2 balances = **1,352 combinations**. It compares eligibility and construction against the rule: equal ranks, count below4 and balance at least20. A separate assertion covers already-split aces. **All 116 Python tests passed**, including previous outcome tests and 300-round session checks. These combinations cover this eligibility grid, not all game states or multi-hand session behavior.
