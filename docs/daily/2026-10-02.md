# 2 October: train once, inspect a frozen policy

## Prerequisites and intuition

A policy chooses actions. Q(s,a) estimates reward after action a in state s. Training changes those estimates; **inference** reads them to make a decision. Review [Q-learning](../lessons/06-q-learning.md) and [the visible-hand lesson](2026-10-01.md) if either distinction is unfamiliar.

A browser game should load a saved, rule-compatible agent and read its estimates. It should not start training whenever the player asks for advice. Keeping the policy frozen also lets repeated requests be checked against the same table.

## The decision, step by step

For observed state s, compare Q(s,stand) and Q(s,hit). If both have evidence:

1. Compute difference d = Q(s,hit) - Q(s,stand).
2. Choose hit if d > 0; otherwise choose stand, including ties.
3. Report both estimates and visit counts so the reader can inspect the comparison.

The original seed-7 Q-learning export at hard 20 versus dealer 10 has stand Q=0.179806 (2,251 updates), hit Q=-0.936884 (118 updates). Difference is approximately -1.116690, so the frozen decision is stand. These are expected-reward estimates, not win probabilities; the difference is not a probability either.

If either action has zero visits, this advice layer returns `action=None` and `status=insufficient_evidence`. It deliberately differs from the evaluation fallback that initializes unseen Q to zero and still chooses an action. Do not report the earlier evaluator's results as measured performance for this withholding advice rule. One or more visits still do not imply reliable advice; low counts and sampling noise remain visible limitations.

## Code walkthrough

[foundations/policy.py](../../foundations/policy.py) adds a small inference boundary:

1. `load_policy` parses a saved JSON file.
2. `FrozenPolicy` reuses the policy-table validator to check artifact type, Foundations rules, alpha where needed, counts, values and stored greedy decisions.
3. It copies each row into internal tuples, so changing the original JSON or a returned advice object cannot alter later answers.
4. `advise` validates the nonterminal observation and reads only that state. It has no environment, hidden cards, random generator or update operation.
5. Its output is a fresh dictionary containing algorithm, observation, decision status and both action values/counts.

The loader supports the existing MC, SARSA and Q-learning control formats. It rejects incompatible rules. A sparse export is allowed; absent states get no recommendation. Validation is not a proof the supplied estimates are accurate or that the artifact came from a trusted trainer. Provenance remains in the source export.

## Run it

From the project root, create a complete export, then inspect a decision:

```sh
python3 -m foundations.q_learning --output /tmp/q-policy.json
python3 -m foundations.policy --input /tmp/q-policy.json --total 20 --dealer 10
```

The first command trains and evaluates once. The second only reads estimates; repeat it without retraining. Add `--soft` to inspect a usable-ace state. A compact experiment record may contain only selected states, so use a full export for later gameplay integration.

python3 -m foundations.local_game --policy /tmp/q-policy.json
