# 13 October: send an action, not a claimed outcome

## Prerequisites and intuition

A client is an interface such as a browser. The environment owns cards, balances and outcomes. A command is a request to act; it is not permission to replace the environment state. Yesterday's terminal called the session directly. Today's small [command boundary](../../public_game/commands.py) gives a future browser adapter a strict data format to use.

## Coding steps

1. Accept a dictionary (the Python representation of a JSON object).
2. Require a known command name.
3. For deal require exactly command, revision and stake; other actions require exactly command and revision.
4. Reject missing/extra fields and invalid revision types. Python booleans are related to integers, so an exact type check rejects True as a revision.
5. Pass the intent to the existing session, which checks funds, phase, action legality and revision before changing state.
6. Return the session's visible snapshot, preserving hole-card concealment.

Example payload: `{'command': 'deal', 'revision': 0, 'stake': 20}`. Stake20 means10 chips because transport units remain half chips. A payload containing `balance: 999` or `profit: 100` is rejected; neither is client-authoritative.

## Worked transition and RL connection

Seed7 starts at200 units. Deal stake20 at revision0 -> balance180, revision1, concealed dealer. Stand at revision1 loses20 net -> balance180, revision2. Normalized result=-20/20=-1. Replaying revision1 fails without drawing or paying again.

The learning loop is observation -> chosen legal action -> environment transition -> reward/next observation. Allowing a caller to supply its own reward would corrupt the data: Q(s,a) would learn from claimed outcomes rather than environment outcomes. This boundary does not yet implement an RL adapter or train any policy.
